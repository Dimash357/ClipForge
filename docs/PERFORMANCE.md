# Производительность длинных видео и прогресс обработки

## Что было не так (1 ч 38 мин, YouTube AV1 1080p60)
* После распознавания звуков запускалось **сканирование экрана по всему видео**. Сначала проход по ключевым кадрам;
  если они редкие (у YouTube AV1/VP9 часто реже раза в 8 с) — второй проход с **полным декодированием на CPU**
  (1 кадр/с) и жёстким таймаутом 30 мин. Один ffmpeg декодирует AV1 1080p60 примерно на 1,4 ядрах: ~1,8× медленнее
  реального времени, т.е. ~3 ч на такой файл → «keyframe scan timed out».
* Сообщение нового шага терялось из-за ограничения частоты записи прогресса — интерфейс показывал «распознаём звуки 99%».
* Динамика кандидатов и сцены клипов (`sample_frames`) тоже декодировали AV1 на CPU с ближайшего ключевого кадра.
* Чтение из ffmpeg-пайпов не следило за зависанием: замолчавший процесс мог держать обработку бесконечно.

## Что сделано
| | |
|---|---|
| Сканирование экрана | Режим выбирается заранее по флагам пакетов (без декодирования). Частые ключевые кадры — один проход, не-ключевые пакеты отбрасываются до декодера (`-discard nokey`). Редкие — видео режется на отрезки, которые декодируются **параллельно** (все ядра CPU или 2 сессии NVDEC); кадры берутся с той же сетки времени и масштабируются тем же фильтром → результат **бит-в-бит** как у последовательного прохода (проверяется тестом) |
| Параллельно с Whisper | Сканирование экрана стартует сразу после извлечения звука и идёт рядом с Whisper и классификатором звуков |
| NVDEC | `studio/accel.py`: проверка декодирования файла на GPU (2 с, один раз на файл), используется для сканирования экрана, выборки кадров (динамика, сцены, вебка) и декодирования при рендере. Декодирование на GPU бит-точное, фильтры остаются на CPU — картинка не меняется. Любой сбой NVDEC → автоматически CPU. `CLIPFORGE_HWDECODE=off` выключает |
| Продолжение из кэша | Готовые отрезки сканирования сохраняются в `screen.part.npz`; пауза, отмена или сбой продолжают с места остановки. Звук, транскрипт, профили — как и раньше из кэша источника |
| Зависания | `procutil.Watchdog`: ffmpeg, не выдающий данных `CLIPFORGE_FFMPEG_STALL` с (300), останавливается с понятной ошибкой. Вместо фиксированного таймаута 30 мин — контроль «живости». В интерфейсе — предупреждение, если прогресс не менялся `CLIPFORGE_JOB_STALL_WARN` с (600) |
| Прогресс | Каждая операция (основной этап + параллельные) — реальный процент, прошедшее и оставшееся время; индикатор «обработка активна» по heartbeat; время каждого этапа сохраняется в задаче |
| Загрузка | CPU (`/proc/stat` / `GetSystemTimes`) и GPU, NVDEC, NVENC, VRAM (`nvidia-smi`), без новых пакетов |

## Настройки
| Переменная | По умолчанию |
|---|---|
| `CLIPFORGE_HWDECODE` | `auto` (NVDEC если работает), `off` |
| `CLIPFORGE_SCAN_WORKERS` | CPU: число ядер (не больше 6); NVDEC: 2 |
| `CLIPFORGE_FFMPEG_STALL` | 300 с |
| `CLIPFORGE_JOB_STALL_WARN` | 600 с |
